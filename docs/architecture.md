# Initial instrument contract

`Instrument` receives explicit contact IDs, white-key indices, monotonic millisecond timestamps and optional normalized velocity. It emits `note_on`, `note_off`, or diagnostic-only `muted` events with key, logical string (0–5), MIDI pitch, chord, zone, intensity and timestamp. Browser pointer IDs and computer keyboard codes are adapters, not hardware scan codes. No interpolation across skipped keys is performed.

One physical key has one active contact action; multiple pointers on that key do not duplicate attacks. Leaving/releasing ends the action; returning is a new press. Different zone keys assigned to the same logical string can overlap. Cancellation/window blur releases all input and cancels lock holds. The UI uses pointer capture so release is observed outside the key area.

The first chord policy is persistent selection. Lock blocks selection and assignment until another continuous five-second hold. Chord transitions affect future attacks only; release events retain the original pitch. Muted presses emit diagnostics but never audio note events. Temporary audio ignores note_off for decay; Silence stops all voices and shared effects. A fixed 14-lane placeholder pool fades the oldest source over 3 ms, then starts its replacement in the same lane. Per-lane filter/gain nodes are reused; each pluck uses a fresh one-shot buffer source with shared, pre-rendered sample data. This is browser implementation policy, not verified FM-1 polyphony.

Zones apply base intensities 0.36, 0.72 and 1.0 multiplied by simulated slider velocity. The audio adapter maps intensity to gain and lowpass cutoff. DSP buffer generation runs in a startup module worker. All configured pitches and three tone families are transferred to a shared cache before Ready; no synthesis loop or sample-buffer allocation occurs during attacks. Diagnostics show attack dispatch/scheduling work rather than end-to-end latency. UI rendering is batched with requestAnimationFrame; diagnostics refresh at 5 Hz outside input dispatch. A real WASM backend must move processing into an AudioWorklet and measure scheduling/output behavior.

Future MIDI proposal (not implemented): channels 1–6 identify strings; note-on pitch follows the selected voicing and velocity maps normalized intensity to 1–127. Track note ownership so release/retrigger sends note-off for the original pitch/channel, including after chord changes; flush all notes on adapter shutdown. Test receiver behavior for overlapping zones and repeated pitches before choosing sustain/retrigger policy. Hardware transport and pressure acquisition remain unverified.

## Upstream AudioWorklet backend

The input model now feeds a selectable second audio adapter, `UpstreamAudio`. It requests the model's 44.1 kHz reference context, compiles a 9.3 KB WASM module, and sends real note-on messages with logical string/pitch/intensity/tone to an AudioWorklet. Fourteen fixed C voice states generate samples live; there is no note-sample cache in this backend. All mixing/model state stays on the audio thread. The UI gets low-rate active/steal/clip/rejection/state telemetry. Source and complete notices live in `third_party/clipper-phys/`; native and WASM use the same independent `dsp/engine.c` adapter. See dsp-feasibility.md for parity, native CPU data and untested hardware limits. The JS adapter described above remains independently selectable.
